## Fase 18.5 — Fallback automático entre modelos gratuitos da Groq
Novo `groq/FallbackModelosGroq.kt`:
- `MODELOS_GROQ_GRATUITOS`: lista fixa, em ordem de preferência (`llama-3.3-70b-versatile` → `llama-3.1-8b-instant` → `gemma2-9b-it` → `llama3-70b-8192` → `llama3-8b-8192`) — os nomes de modelo são o ponto mais instável da API da Groq (ela os desativa/renomeia com frequência), então a lista existe para o app continuar funcionando mesmo se um nome específico parar de responder, sem precisar de atualização.
- `enviarComFallback(cliente, mensagemUsuario, promptSistema?, modelos?)`: chama `GroqClient.enviarMensagem()` (Fase 18.4) para cada modelo da lista, em ordem, até o primeiro `Sucesso` — retorna também qual modelo respondeu (`ResultadoComFallback.Sucesso.modeloUsado`), útil para diagnóstico. Sem sucesso em nenhum, retorna a última falha observada.
- Curto-circuito inteligente: erro de API key inválida/expirada (HTTP 401) para IMEDIATAMENTE, sem tentar os demais modelos — trocar de modelo não resolve um problema de autenticação, só atrasaria a resposta ao usuário. Demais erros (modelo indisponível, limite de uso, serviço fora do ar) avançam normalmente para o próximo modelo da lista.

ASSUMINDO: lista de 5 modelos gratuitos escolhida por serem, no conhecimento geral disponível, os modelos gratuitos mais estáveis oferecidos pela Groq — como a própria API pode mudar nomes de tempos em tempos (aviso já presente na tela do Assistente, Fase 18.2), a lista é um `val` de nível de pacote, fácil de ajustar depois sem mexer na lógica de fallback. Reconhecimento do erro de chave por correspondência de texto na mensagem de `GroqClient` (não por um código de erro tipado) — simples o suficiente para o escopo desta fase; se `GroqClient` crescer com mais tipos de erro identificáveis no futuro, vale revisitar com um enum de causa em vez de string.

## Fase 18.4 — Cliente HTTP da Groq
Novo pacote `groq/`, arquivo `GroqClient.kt` — `HttpURLConnection` nativo (sem Retrofit/OkHttp), mesmo princípio leve já usado por `AtualizacaoRepository`/`CatalogoRepository` (Fases 2.3/8).
- `enviarMensagem(modelo, mensagemUsuario, promptSistema?)`: monta o corpo JSON (`model`/`messages`, com `system` opcional), autentica via header `Authorization: Bearer <apiKey>` (chave recebida no construtor — vem de `AssistenteIARepository`, Fase 18.1, nunca hardcoded), envia POST para `https://api.groq.com/openai/v1/chat/completions` e extrai o texto de `choices[0].message.content`.
- Retorna um `sealed class Resultado` (`Sucesso(texto)` / `Falha(motivo)`) em vez de lançar exceção — mensagens de erro traduzidas por código HTTP (401 chave inválida, 404 modelo indisponível, 429 limite atingido, 5xx serviço fora do ar) sem expor detalhes internos da API.
- Só faz UMA chamada para UM modelo específico — a lista de modelos gratuitos e o fallback automático entre eles ficam para a Fase 18.5, que vai chamar `enviarMensagem()` em sequência até obter `Sucesso`.
- Chamada de rede síncrona/bloqueante — cabe ao chamador (Fase 18.5+, dentro de `AssistenteIAActivity`) rodar em `Dispatchers.IO`, mesmo padrão de `lifecycleScope.launch { withContext(Dispatchers.IO) { ... } }` já usado no restante do app.
- Timeout de 15s (mais generoso que os 8s do `AtualizacaoRepository`, Fase 8) por ser uma chamada interativa disparada pelo curador, não uma sincronização silenciosa em segundo plano.

ASSUMINDO: formato de requisição/resposta segue a API "OpenAI-compatible" da Groq (`chat/completions`, `messages` com `role`/`content`, resposta em `choices[0].message.content`), documentada publicamente pela Groq; nenhuma chave de API foi embutida no código — `GroqClient` sempre recebe a chave já salva pelo usuário (Fase 18.1) como parâmetro do construtor. Sem streaming de resposta (a Fase 18 não pede resposta incremental, e resposta única mantém o cliente mais simples).
